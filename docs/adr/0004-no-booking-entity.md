# ADR-0004 不建模预订实体

- 状态：已采纳
- 日期：2026-11-12

## 背景

船单是由“已确认的预订”汇聚而来的。很自然会想建一个 Booking 实体，把预订的创建、支付、退改都纳进来。

## 决策

系统**不拥有**预订数据。只接收“已确认预订”的结果（人、船次、等级、专长），系统边界从预订确认之后开始。

## 理由

1. 范围边界是刻意的：课程作业只做“预订确认后、离港前”。
2. 建模 Booking 会把支付、退改、库存一并拖进来，边界失控。
3. 取消预订可以用“移除人员”的变更事件表达，走同一条链路，不需要新实体。

## 代价

系统内无法发起退改，只能被动接收变更；预订重复要靠 R-08 兜底，而不是数据库唯一约束。

## 备选方案

- **完整建模 Booking**：更接近真实系统，但会把项目拖成“预订 + 船单”两个系统。

## 影响

- 快照里只有 `Diver`、`Instructor`，没有 Booking。
- “新增 / 移除 / 换人”都表现为快照变更，进而生成新版本。
